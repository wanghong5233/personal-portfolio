# 踩坑 03：从分块选场到全文直喂

## 一句话

我发现结构化抽取链仍沿用小上下文时代的分块/选段设计，导致低频实体丢失、多次重复输入和排队超时；在验证常见长文本可放入大上下文模型后，将相关核心链改成全文单次调用，并保持下游契约不变。超长文本仍按预算分层处理。

## 背景

旧模型上下文只有几千到几万 token 时，长文本必须分块，因此形成了：

- 实体先解析、再消歧、再补全；
- 实体画像只选择部分文本单元；
- 摘要不同字段由不同链生成；
- 非标准文本依赖规则硬切；
- 同一份原文被多个调用重复发送。

这套设计在当时合理，但模型上下文扩大后没有自动失效检查。

## 症状

- 实体画像只看前段内容，后续变化为空或失真；
- 低频实体因选段规则被遗漏；
- 实体表、关系图和画像由不同调用生成，可能互相矛盾；
- 摘要字段被硬切或依赖不完整片段；
- 一次分析拆成几十个小调用，在并发限流下排队；
- 非标准原料可能被规则切成不合理的单元。

## 初始错误方向

### 1. 继续调选场策略

可以增加头中尾采样、角色时间线采样和更多 fallback，但规则复杂度持续增长，仍不能保证全文可见。

### 2. 分别优化每条 prompt

人物表、关系和小传如果输入不同，prompt 再好也可能产生事实分叉。问题不只是生成质量，而是信息边界不一致。

### 3. 所有输入都交给 LLM 重切

标准剧本已经写明集场，重新让 LLM 猜会破坏原结构，还增加成本。LLM 标准化只能用于规则真正无法识别的输入。

## 关键判断

当时主力模型拥有大上下文窗口，而常见长文本规模明显低于其上限。于是需要重新问：

> 分块仍是必要约束，还是已经变成历史负债？

结论是：对于需要全局理解、且全文明显低于上下文上限的结构化抽取和摘要任务，分块的损失已大于收益。

## 最终方案：适中长文本全文输入，超长文本按预算分层

### 实体全文抽取

适中长文本一次调用统一产出：

- 实体；
- 实体关系；
- 实体画像。

三者共享同一标识空间。关系摘要由关系边派生，不再让模型对同一关系事实回答两次。

### 摘要全文抽取

适中长文本一次调用产出：

- 主线与冲突；
- 一句话概要；
- 详细摘要。

阶段类型使用受控词表，输出后做结构校验；失败时只允许一次有方向的 repair。

### 非标准原料标准化

- 先由确定性规则识别格式；
- 只有判定为 `single_scene` 等无法识别结构时才调用 LLM；
- 已显式标注的结构单元不重切；
- 被剥离的标题、作者、实体表等内容进入元数据区，保持零丢失账目。

### 兼容迁移

- 保持持久化、读取和报告数据契约不变；
- 只替换上游生成方式；
- 用现有前端报告验证消费端无需同步重写。

### 长文快路径

超长文本不机械全文输入，而是按结构锚点和 token 预算选择输入，并跳过高成本链。这样避免把针对常见文本成立的结论扩展到极长原料。

## 取舍

**收益：**

- 全文覆盖，减少低频角色和后段剧情丢失；
- 关联字段来自同一次模型理解；
- 减少重复输入和调用数量；
- 报告并行调度更简单。

**代价：**

- 单次输入和输出预算更高；
- 一次调用失败影响字段更多；
- 对模型长上下文能力依赖更强；
- 非标准文本的虚拟集场仍可能不符合创作意图。

因此不是“全文永远优于分块”，而是针对任务、模型和真实 token 分布重新做选择。

## 验证

- 用真实 badcase 对比实体、摘要和调用耗时；
- 检查低频实体、开头中段结尾的变化和关系一致性；
- 保持下游 schema 与持久化契约不变；
- 增加并行调度测试；
- 对非标准原料记录标准化与元数据剥离结果；
- 后续按虚拟结构单元 badcase 继续回归。

## 结果与局限

**已确认：**

- 全文实体和全文摘要模块可接入分析链；
- 适中长文本走全文输入，超长文本仍支持分层输入；
- 旧分段实体管线的架构前提被正式替代；
- 非标准原料只在规则无法识别时触发 LLM 标准化。

**仍有限制：**

- 没有足够真实样本证明所有长剧本都优于分块；
- 超出上下文或极长原料仍需要降级策略；
- 模型可能在长输入中漏掉局部细节；
- 虚拟集场必须标明是系统推导。

## 业务影响

实体与摘要是用户理解陌生长文本的核心入口。旧方案会让结果看似完整，却缺后段变化或关键关系。全文输入减少了这种系统性盲区，也降低了多调用排队造成的失败和成本浪费。

## 证据

来自实习中的真实故障与对照实验（细节已脱敏）。

## 面试追问

**为什么不是一开始就全文？**  
早期模型窗口和延迟约束不同；架构是对当时约束的响应，问题在于约束变化后要重新评估。

**一次调用产出多个字段会不会更难 repair？**  
会，所以使用受控 schema、动态输出预算和有界 repair；同时通过共享事实空间减少跨调用矛盾。

**如何处理超过上下文的剧本？**  
当前长本路径会跳过部分高成本模块；极长输入仍需按任务设计分层或分块，不能机械全文。

**怎么证明不是只减少调用次数？**  
验证重点还包括低频角色、后段弧线、关系一致性和原文覆盖，而不是只看 latency。
