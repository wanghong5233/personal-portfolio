# 踩坑 05：Agent 写回竞态与副作用验证

## 一句话

为了加速多段内容改写，我尝试让多个 Agent 并行修改同一个编辑器，结果出现节点竞态、diff 丢失和重复劳动；我改回单 Agent 批量修改，并在工具层校验文档是否真实变化，防止“模型说改了但页面没改”。

## 背景

报告页会给出改进建议。用户点击后，报告页 Agent 需要：

1. 定位相关场景；
2. 读取必要上下文；
3. 修改共享富文本编辑器中的文档；
4. 在编辑器展示 diff；
5. 用户确认后写回。

当一次建议涉及多个文本单元时，并行 Agent 看起来可以降低延迟。

## 并行方案

初始设计让多个 Agent 分别处理文本单元，再合并修改。它在纯文本任务上看起来合理，但实际共享：

- 同一个富文本编辑器实例；
- 同一组节点 id；
- 同一份 diff 状态；
- 同一篇不断变化的文档。

## 失败现象

- 多个 Agent 读取的是不同时间点的文档；
- 一个 Agent 修改后，另一个仍持有旧 node id；
- 部分改动绕过统一 diff；
- accept-all 不完整或修改相互覆盖；
- 多个 Agent 重复理解相同上下文，成本并未按预期下降；
- 聊天中返回“已完成”，但页面可能没有任何变化。

## 根因

并行任务并不独立。它们共享一个有状态、带版本的编辑器：

> 文本改写可以按场景拆分，但写入副作用不能假设可交换、可并发。

同时，工具调用的“成功返回”只说明代码路径结束，不证明文档状态真的变化。

## 决策：显式回滚

我没有继续用锁和补丁合并把复杂架构硬撑下去，而是撤回并行方案：

- 使用单个报告页 Agent；
- 一次任务内批量修改目标节点；
- 保持读取、修改和 diff 在同一文档版本上；
- 复用编辑器统一的 diff 接受/拒绝流程。

这个方案理论并行度更低，但状态模型简单、用户可核查，整体成功率更重要。

## 第二层修复：验证真实副作用

在编辑器工具层增加后置校验：

1. 修改前序列化文档；
2. 执行节点修改；
3. 修改后再次序列化；
4. 如果内容没有变化，返回显式失败；
5. Agent 根据错误重新定位或向用户说明，而不是声称成功。

这将“是否完成”从模型叙述改为系统可验证事实。

## 其他配套

- 发送任务前重新解析选区和文本锚点；
- 占位符或无法定位的节点拒绝写入；
- 长文只提供段落索引和相关片段，避免整页上下文；
- 报告入口与手动编辑入口复用同一 Agent 会话和 diff 链；
- 工具 trace 记录调用、耗时和成功标志，不记录敏感全文。

## 为什么不加锁继续并行

加锁只能把写操作串行化，不能自动解决：

- Agent 基于旧版本生成的补丁；
- 跨场景设定和文风依赖；
- diff 合并冲突；
- 多次重复读取与模型成本；
- 用户如何审阅多个并发修改。

在当时的任务规模下，单 Agent 批量操作是更小、更可靠的状态模型。

## 验证

- 构造多场景批量改写；
- 检查所有修改都进入统一 diff；
- 检查 accept-all/reject 行为；
- 构造找不到节点、替换前后相同等 no-op；
- 确认 no-op 显式失败；
- 检查会话与编辑器 remount 后任务仍绑定正确文档。

## 结果与局限

**已确认：**

- 并行 Agent 方案已明确撤回；
- 现行写回使用单 Agent 和统一 diff；
- 编辑器运行时对 silent no-op 采用 fail-loud。

**仍有限制：**

- 单 Agent 批量修改的延迟可能更高；
- 复杂长文的上下文连续性仍依赖检索与场景选择；
- 全文序列化对比主要防 silent no-op；它只能证明某处发生变化，不能单独证明目标节点被正确修改；
- 更严格的验证还应核对目标节点版本、预期节点集合或实际 patch；
- 正确性仍需用户 diff 审阅。

## 业务影响

如果 Agent 只在聊天中声称完成，或者并发写回互相覆盖，用户会失去对系统的基本信任。对于内容生产，可靠写回和可审阅 diff 比表面并行速度更重要。

## 面试追问

**为什么多 Agent 不一定更快？**  
任务共享上下文和写入状态，拆分后增加重复理解、冲突和合并成本；理论并发不等于端到端完成更快。

**如何定义工具调用成功？**  
不仅是函数未抛错，还要验证预期副作用发生；对写操作至少比较修改前后状态。

**发生变化是否代表修改正确？**  
不代表。副作用校验只防 no-op；目标节点和 patch 还应单独核验，语义正确仍靠约束、上下文和用户 diff 审阅。

**什么时候可以重新并行？**  
当任务能按互不重叠的文档分区、补丁基于明确版本、冲突可检测且合并策略可验证时。
