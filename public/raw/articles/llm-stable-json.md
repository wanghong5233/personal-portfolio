# LLM 稳定抽取 JSON

LLM JSON 抽取有三个独立验收面：语法可解析、契约合规、业务事实正确。前两项通过不代表第三项通过；模型窗口允许某段输入，也不代表模型能稳定利用其中全部信息。

生产实现通常优先使用 provider 原生 `json_schema`、strict tool call 或自托管 constrained decoding；只支持 JSON mode 时，补应用侧强校验和有界 repair。原生约束保证的是受支持 schema 子集内的输出形状，不保证字段与原文一致，也不替代业务验收。

## 判断原则

先分两层，再选手段：

| 层 | 问什么 | 例 |
|----|--------|----|
| 结构 | 能否解析？形状/类型是否过校验？ | 半截对象、`score` 成了字符串、缺必填键 |
| 语义 | 字段是否真实、完整、可核对？ | 类型对但全空；枚举胡选；有结论无证据 |

Pydantic / Zod / JSON Schema 可以校验类型、范围、枚举、长度和可编码的跨字段不变量，但不能证明事实来自原文。边界校验应关闭不需要的类型强制转换、拒绝未知字段；否则 `"3"` 被转成 `3`、多余键被忽略，也可能制造假通过。

再问三个边界问题：

- 当前 provider、模型和 endpoint 实际保证到哪一级：语法 JSON、受支持 schema 形状、还是什么都不保证？同一模型的普通回复和 strict tool call 可能不同。
- 字段是否共享同一份上下文、证据标准、失败语义和重试策略？不共享时应拆步；字段数量本身不是拆分依据。
- 输入数据形态是否已超过本模型×本任务的有效区？窗口硬顶只说明塞得下，不说明中间内容仍被同等对待。

合法 JSON ≠ 字段齐全 ≠ 字段可信。流程成功 ≠ 覆盖了声明范围的数据。上下文很大 ≠ 应该一次吐完整画像。

## 能力阶梯

按可靠性选，不按方便选：

1. **Constrained / native structured output**：对 provider 支持的 schema 子集，正常完成时提供强结构保证。仍要处理拒答、空内容、截断、unsupported schema 和业务值错误。
2. **JSON mode**（仅保证 JSON 语法）：必须配合 schema 校验与 repair。启用条件以 provider 文档为准；DeepSeek V4 普通回复要求 prompt 出现 `json`、提供目标格式样例并预留足够输出预算。其 beta strict tool call 属于上一层，但支持的 schema 关键字与普通 JSON Schema 不完全相同。
3. **纯 prompt + 事后截取**：只作兜底，不能当主路径。

验证闭环固定为：约束（有则用）→ 解析 → 严格 schema 校验 → 确定性业务规则 → 有界 repair（反馈具体错误 + 最小合法样例）→ 仍失败则降级或失败。重试次数按任务成本和实测成功率设定并硬封顶。

Provider 没有严格 schema 约束时，具体输出样例通常比抽象格式说明更有效；repair 同时给出上次的校验错误，避免无目标重跑。只有任务确实需要显式推理时，才考虑在结论前输出简短依据；字段顺序会影响自回归模型，但效果依赖模型和任务，必须 A/B 验证。纯事实抽取不应为了套模板生成无依据的 reasoning。

## 编排口径

能代码算的不要问模型。必须问模型时：

- **契约明确**：必填字段、未知字段策略、严格类型、枚举、范围和列表上限都要显式；先确认 provider 支持这些 schema 关键字。
- **按失败边界拆步**：上下文、证据标准或降级策略不同的字段分开抽，再确定性汇编。拆分会增加调用和归并错误，不能只凭字段多就拆。
- **超过有效区时选择可验证的长文策略**：可局部分解的任务用分块 map + reduce；存在跨块依赖时保留重叠、全局索引或再做全局校验。分块会引入依赖丢失、冲突和归并误差，必须与整文基线对测。
- **只修可判定的语义缺陷**：原文强信号与必填证据可用规则检查，再定向重抽；不能把「字段短」直接等同于质量差，也不能靠反复催模型写长。
- **降级服从产品契约**：允许部分结果时，单步可 degraded、可选字段留空并告警；要求原子完整时，必需字段过不了门就整单失败。

## 剧本分析中的真实经验

**Schema repair 有效，但只解决结构错误。** 首次加固给 JSON 调用补了 Pydantic 校验和一次 repair；随后人物与节拍链真实出现过 dict-as-list、字段缺失等 schema 错误。Repair prompt 从整份 schema dump 改成「具体校验错误 + 最小合法样例」后，内部观测的单轮修复成功率约从 50% 提升到 85%。该结果支持在当时模型与任务上保留样例式 repair；更换模型或契约后需要重新测量，且不能据此推导业务字段已经正确。

**输出预算错误会伪装成 JSON 质量问题。** 一次真实运行中，87 次调用有 27 次失败：经网关调用的 thinking 模型消耗了 completion 预算，返回空内容或半截 JSON，`finish_reason=length`；旧策略只是用相同预算切换 provider，结果仍然截断。改为同模型预算翻倍、有界升级，并为 thinking 预留预算后，同一坏例回归达到 57/57 次调用成功。遇到 `length` 必须结合 token usage、模型上限和总上下文判断：输出预算不足才增加输出预算；总上下文不足则应减少输入或分块。固定翻倍次数不可跨模型照搬。

**语义质量不能靠“嫌短催长”。** 人物小传曾对身份为空、外貌全空、人物描述过短触发字段级 refine；后续真实复盘发现更根本的问题是只读前部少量场景，模型看不到中后段人物变化。链路最终删除了按长度催写的 critique/refine，改成按人物时间线采样头、中、尾场景，逐条核验原文引文，并由代码按覆盖、跨度和证据可核验率计算质量。高置信业务不变量仍可定向修复；主观的「不够长、不够丰富」不应成为自动重试条件。

**输入覆盖和证据接地比“更大窗口”重要。** 人物关系抽取曾固定最多选择 14 个场景、每场只保留 360 字；超过上限的场景不会进入该次关系判断，链路却仍可能正常返回 JSON。后续改为预算驱动分块、map-reduce 合并，并记录 `fed/total/dropped`。进一步实验把单块上限与模型窗口解耦，按真实评测标定；关系证据必须能在对应场景原文中定位，无法定位的关系类型、极性和引文不进入可信结果。

## 禁止模式

- 相信「已按 JSON 输出」或「JSON mode 已开」即验收通过。
- 只有 JSON mode，没有应用侧 schema / 业务校验。
- 默认类型转换或忽略未知字段，使错误输出被“修”成合法对象。
- 使用 provider 不支持的 schema 关键字，却假定服务端已经强制执行。
- 超大嵌套对象一次抽完，靠运气和一次 repair。
- 输出预算按中位数填充估算；截断无日志。
- 输入用固定条数/字数窗静默切片，流程仍标成功。
- 窗口很大就取消分步与分块。
- 无视跨块依赖和归并冲突，机械套用 map-reduce。
- 用缓存回放冒充跨次稳定性。
- 结构失败整单死亡，或语义全空仍给高置信。
- 把 A 域标定的切窗/重叠率未验证抄进 B 域。

## Agent 执行规则

接到「抽 JSON / 加 LLM 步骤」时默认：

1. 按 provider × model × endpoint 核对 JSON mode、strict schema、支持关键字和异常返回；不能从兼容 OpenAI SDK 推导能力等价。
2. 先写严格契约；上下文、证据或失败语义不同才拆步。校验失败有界 repair，再失败按产品契约降级或失败。
3. 先给字段和列表设业务硬顶，再按最坏情况推导输出预算；输入超有效区时选择经真实样例验证的分块或层级策略。截断、丢块、超时必须可观测。
4. 只对高置信业务不变量设置规则门；主观质量问题先检查输入覆盖、任务定义和证据，不默认追加 refine。
5. 验证同时覆盖结构和语义：契约测试防格式回归，真实 badcase / golden 样例度量准确率、召回、证据与覆盖。

验收至少覆盖：schema 通过率、repair 触发率、`finish_reason`、输入覆盖率、关键字段 precision/recall、证据可定位率，以及分块相对整文基线的回退。
