# 测试治理

测试不是开发仪式，也不是给 Agent 消耗 token 的安全感。代码、类型、日志、真实运行和测试都是验证手段；测试只有在能用较低成本稳定提升发布信心时，才是资产。

业界共识并不复杂：Google 强调测试行为而不是实现细节，Martin Fowler 的 Test Pyramid 关注测试组合的速度和维护成本，Kent C. Dodds 的 Testing Trophy 强调投入产出比和“mostly integration”。它们指向同一件事：测试要验证生产用户或真实调用者关心的行为，而不是复制当前实现。

失真的测试比没有测试更坏。它会制造第二套假的世界：mock 的外部服务不符合真实契约，fixture 脱离真实数据分布，断言绑死历史实现，最后代码为了通过测试而不是为了修复产品问题而变化。AI coding 下尤其危险，因为 Agent 会把“跑了测试”误当成“验证过真实风险”。

## 判断原则

先问风险，再选验证方式：

- 这个修改会改变用户可见行为、数据契约、状态流转、权限、账本、持久化、并发、重试、降级或外部服务调用吗？
- 这个 bug 是否曾经真实发生，且未来容易回归？
- 这个逻辑是否有复杂分支、边界条件、预算截断、时间/随机性，靠阅读不容易确认？
- 不写测试时，是否仍能用类型检查、lint、局部脚本、日志、真实样例或手动验收低成本确认？

如果只是文案、注释、文档、类型内缩、小范围命名、删除死代码，通常不需要跑测试；最多做静态检查或人工 diff 复核。明明可以确定的小修改，不应该为了形式跑全量测试。

## 选择口径

测试要贴近真实风险，优先顺序通常是：

- 静态检查：类型、lint、格式、schema 校验，适合发现低级错误和契约错位。
- 目标单测：纯函数、复杂算法、边界条件、预算计算、确定性转换。
- 集成测试：服务层、store、router、数据库读写、状态机、多个模块协作。这里往往比过度 mock 的单测更有价值。
- 契约测试 / golden case：外部服务、LLM 输出 schema、真实 badcase、关键数据样例。
- 端到端测试：只覆盖核心用户路径和高风险回归，不作为每个小改的默认验证。

成熟做法不是追求覆盖率数字，而是追求信心密度。测试数量增加但信心不增加，就是膨胀。

## 禁止模式

- 为了“有测试”而写测试。
- 断言私有函数调用顺序、内部变量、临时结构，而不是外部可观察行为。
- 大面积 mock 自己的业务模块，导致集成关系完全没被测到。
- 用假数据覆盖真实问题：真实 bug 来自长文本、真实日志、真实 provider，就不要只造三行 toy fixture。
- 让测试固定历史实现，阻止正确重构。
- 对文档、注释、显然安全的小改默认跑全量测试。
- 测试失败后不查根因，只继续补 mock、改断言、跳过测试。

## Agent 执行规则

Agent 修改代码时默认选择最窄的有意义验证，并说明为什么够用。测试选择应随风险升级，而不是随文件数量机械升级。

没有行为变化的文档 / 注释改动：不跑测试。  
小范围确定性代码改动：跑相关静态检查或目标单测。  
共享契约、状态机、数据结构、服务边界变更：跑对应集成测试或契约样例。  
LLM prompt、解析质量、召回、排序、切分：不要迷信 mock 单测，优先真实 badcase / golden sample / quality probe。  
性能、超时、并发、重试：需要真实日志、局部压测或可观测指标，普通单测只能防结构回归。

新增测试前必须先回答：它防的真实风险是什么？它比阅读、类型检查、日志或真实样例更合适吗？它失败时会指向产品问题，还是只说明实现换了？

好测试短、真、稳：输入接近真实，断言接近用户或调用者关心的结果，失败能定位风险。坏测试假、脆、贵：mock 世界自洽，断言实现细节，维护成本超过保护价值。
