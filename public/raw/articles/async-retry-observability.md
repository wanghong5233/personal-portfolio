# 异步重试边界与可观测性

> 来自实习中的真实故障与对照实验（细节已脱敏）。  
> 目标：把「重试、可观测、成本归属」从概念变成可复述的工程案例。

---

## 1. 这次到底解决了什么

已有异步队列、缓存与任务表后，系统仍有三个缺口：

1. 成本归属只到用户、资源和意图，缺 `task_id`（排障时无法把网关成本和具体任务一键对齐）。
2. worker 顶层异常策略是「统一 failed」，没有区分「瞬时故障可重试」和「终态业务错误应立即失败」。
3. 缺一个轻量可观测入口（队列深度、任务状态分布、最近失败样本），排障要手查多处。

---

## 2. 关键设计：任务级重试不等于盲目重试

### 2.1 错误分类

- **瞬时错误（可重试）**：网络抖动、超时、限流、连接异常（`APIConnectionError / APITimeoutError / RateLimitError / httpx.TimeoutException` 等）。
- **终态错误（不可重试）**：输入质量或业务校验问题（例如 `EmptyScriptError`、扫描件无法解析、结构化 schema 错误等）。

### 2.2 策略

- 对瞬时错误：按指数退避重试，并把重试信息写入任务进度。
- 对终态错误：直接标记任务失败并返回，不再继续消耗模型额度。

一句话：**能自动恢复的才自动重试；输入本身有问题就 fail-fast。**

### 2.3 重试的前提是幂等（这次真踩到的坑）

增加异步任务重试次数后，复盘时发现一个**隐藏的静默数据损坏**：

- 分析任务流程是“结构化入库 → 生成结果”。
- 一旦入库成功、生成阶段抛出瞬时错误，队列可能**整体重跑任务**，再次执行入库。
- 若入库是纯 INSERT、每次生成新标识且无去重，同一资源就会被写入两套结构单元，**且不报错（fail-silent）**，污染所有下游分析。

第一性原理：**异步队列是 at-least-once 投递，任务一定会被执行多于一次；要拿到 effectively-once，必须让任务幂等。**

修复选型（A vs B）：

- **A（worker 守卫：已完成就跳过入库）** = checkpointing，能省重复解析/LLM 开销，但依赖状态标志当检查点、不是正确性边界 → 归为「可选优化」。
- **B（写库幂等：同事务覆盖或 upsert，以资源标识为幂等键）** = 根因修复，跑 N 次等于跑 1 次，与调用方/重试次数无关 → **采用**。

为什么不直接用复合唯一约束当 fail-aloud 兜底？

- 实测存量数据：同一长文本里**多数结构键只出现一次、个别键天然重复**（来源编号复用或兜底规则命中同号）。
- 编号是**带语义的来源字段、本就不一定唯一**，加唯一约束会**误杀合法入库**。
- 教训：**加 DB 约束前必须先验真实数据分布**，别凭直觉。

fail-aloud 应放对层级：终态错误即时失败 + 覆盖写旧数据时打 `WARNING` 日志 + 重试信息进入任务进度与 metrics —— 让「重新入库」可见，而不是用一个会误伤的约束硬卡。

## 3. 成本归属为什么要加 task_id

网关请求元数据原本只记录用户、资源和意图；随后补充任务标识。

收益：当某次任务出现「耗时高 / 重试多 / 成本异常」时，可以按 `task_id` 直接关联：

`任务状态 ↔ 网关请求轨迹 ↔ 成本记录`

这在面试里可以回答「你们怎么做请求级归因」。

---

## 4. 可观测性为什么选轻量端点，不上大平台

本阶段目标是「开发期可定位问题」，不是一次性搭完整 observability 平台。

所以只增加一个受强鉴权保护的管理指标端点，输出：
  - 队列深度；
  - 任务状态分布（pending/running/success/failed）；
  - 最近失败任务样本。

这已经够支撑日常排障和回归验收；后续如果并发规模上来，再接入更重的指标体系（Prometheus/Grafana 等）更合理。

---

## 5. 可复述的工程取舍（面试高频）

### Q1：为什么不是一上来就 DLQ + 自动重放？

因为现阶段已有可控的手动重放入口，先把**错误分类 + 可观测**做扎实，收益更高、复杂度更低。

### Q2：你们怎么避免重试把成本打爆？

通过「终态错误不重试」+「瞬时错误指数退避、次数上限」两道闸。

### Q3：怎么证明是生产思维，不是 demo 逻辑？

看三个关键词：

- **归因完整**：成本维度补齐到 task 级。
- **策略分层**：输入错误 vs 基础设施错误分开处理。
- **可观测闭环**：从接口直接看到队列与失败样本，而不是只看日志猜。
